# `gateware/` — our own FPGA design for the Colorlight E120

A from-scratch ECP5 bitstream for the E120 receiving card, so a P2.5 128×64
1/16-scan panel of SM16269S drivers can be driven with the chip protocol under
our control instead of the vendor's.

**This is a skeleton.** The pin constraints, the clocking, the protocol
constants and the module boundaries are real and evidence-backed. The state
machines are not implemented. Read
[`docs/own-gateware/PLAN.md`](../docs/own-gateware/PLAN.md) first — it carries
the feasibility argument, the recovery strategy, the unknowns and the
milestones. This file is just the map of the directory.

## Nothing here programs the card

There is no `flash` target in the Makefile, deliberately. Programming is a
separate, manual act.

Over Ethernet, writing the primary flash bank is **irreversible**: every path
that writes it today needs the vendor gateware running, so a bitstream that
fails to bring up Ethernet cannot be replaced by the thing it replaced.

Over **JTAG** it is not irreversible at all — and that is the whole
development story. A bad bitstream cannot brick an ECP5 (failure leaves `INITN`
low, `DONE` low, SRAM erased, nothing written), and the ECP5's JTAG-to-SPI
bridge is enabled by default in exactly that unconfigured state, so a card that
refuses to configure is the *easy* case to recover. Better still, `ecpprog -S`
/ `openFPGALoader -m` load a bitstream into **SRAM only** — the flash is never
touched and a power cycle restores the vendor image.

**So: find the JTAG pads first (PLAN.md §6.1, experiment E-JTAG), then develop
entirely in SRAM, and write flash only when something works.** The one thing
still needed is knowing where TCK/TMS/TDI/TDO come out on this board, which the
spec photo cannot resolve.

## Layout

| path | what |
|---|---|
| `e120.lpf` | pin constraints. Every entry cites its evidence and its confidence. Pins that are not known are commented TODOs, never guesses. |
| `rtl/top.v` | top level, four build targets (blink / echo / flash / hub75) |
| `rtl/pll125.v` | 25 MHz → 125 MHz, generated by `ecppll`, divisors identical to the vendor's |
| `rtl/rgmii_rx.v` | RGMII receive, with the lane permutation left as a parameter |
| `rtl/mac_rx.v` | preamble strip, MAC filter, FCS check |
| `rtl/eth_crc32.v` | Ethernet FCS |
| `rtl/frame_parser.v` | the Colorlight `0x55` / `0x0107` / `0x0A` wire format |
| `rtl/framebuffer.v` | 128×64×3×8 in EBR, six lanes |
| `rtl/spwm_engine.v` | SM16269S command tails, config writes, grey upload, RCLK |
| `Makefile` | yosys → nextpnr-ecp5 → ecppack |

## Toolchain

`make tools` prints the current state and the exact install commands. On this
machine right now:

* `ecppack`, `ecpmulti`, `ecpunpack`, `ecppll`, `ecpbram` — **installed**
  (Homebrew `prjtrellis` 1.4_9)
* `yosys` — **missing**, `brew install yosys` (homebrew-core has 0.68)
* `nextpnr-ecp5` — **missing and not in homebrew-core.** Use the OSS CAD Suite
  `darwin-arm64` tarball, or build from source against the Homebrew prjtrellis.

If you take the OSS CAD Suite route you will have two prjtrellis databases on
the machine. Set `TRELLIS_DB` explicitly; a mismatched database produces a
bitstream that is wrong in ways nothing will warn you about.

## The one thing to keep straight

The SM16269S has **no OE pin**. The HUB75 connector's OE wire carries the
chip's `RCLK`, which is simultaneously the greyscale clock and the row advance,
and it must free-run continuously — including during data upload. If you find
yourself writing code that holds OE at a level to blank the display, stop: that
is the previous chip family's habit and on this part it means the panel never
lights at all.

## Why Verilog

Yosys reads Verilog-2005 natively with no wrapper, the ECP5 primitives
(`EHXPLLL`, `IDDRX1F`, `DP16KD`, `USRMCLK`) are documented in Verilog, and
`ecppll` emits Verilog directly. Amaranth or SpinalHDL would add a language
runtime between us and a toolchain we are already going to be debugging. The
design is small enough that the productivity argument does not bite.
