E120 SPI-flash address map — derived 2026-09-01 from card-dumps/ vs third-party/firmware/
Reproduce with: python3 analysis/fpga/flash-map.py
All offsets are absolute flash byte addresses. 64K blocks; "blk" = addr>>16.

=============================================================================
A. WHAT EACH DUMP FILE IS
=============================================================================
primary-region.bin        0xC0000 bytes  = flash 0x000000-0x0BFFFF (blocks 0x00-0x0B)
primary-after-restore.bin 0xB0000 bytes  = flash 0x000000-0x0AFFFF (blocks 0x00-0x0A)
golden-bank.bin           0xB0000 bytes  = flash 0x200000-0x2AFFFF (blocks 0x20-0x2A)

Alignment of a vendor .hex into flash is delta = 0: .hex byte 0 -> flash byte 0
of the bank base. The 128-byte size difference (721024 - 720896) is trailing
0xFF/end-marker padding at .hex 0x0B0000-0x0B007F that is simply not dumped;
it is NOT an alignment offset. (HIGH: the Lattice ASCII header and every
bitstream command byte line up exactly at delta 0.)

0x034000-0x03FFFF   erased (0xFF)
0x040000-0x04FFFF   DATA. 16384 x the constant 4-byte word 99 99 99 08, nothing

0x070000-0x07AFFF   THE COMPILED BOOT CONFIG IMAGE (docs/compiled-image-format.md).
   0x070000+0x0000  basic-parameter pack body (a8 ff ff ff 20 80 02 10 ...)

   0x070000+0x0500  data-swap pack
   0x070000+0x0600  module-position pack

   0x070000+0x0A00  current segment
   0x070000+0x0C00  current exchange
   0x070000+0x0D00  (no directory entry) -> ERASED (0x070D00-0x070FFF = FF)
   0x070000+0x1000  void-line packs 0-1
   0x070000+0x1800  anti-void-line packs 0-3 (ends 0x0727FE; 0x072800-0x072FFF FF)

0x07F100-0x07FFFF   erased (0xFF)

C. PRIMARY BANK AFTER OUR RESTORE (primary-after-restore.bin)
=============================================================================
Byte-identical to E320_PCB6.0_PWM_FPGA10.81_20230907.hex over the whole
0x000000-0x0AFFFF, with EXACTLY ONE exception:
   0x07F000-0x07FFFF  4096 bytes, all 0xFF (erased)
4042 of those 4096 bytes differ from the vendor file (54 already were 0xFF).
Nothing else differs. (HIGH — single contiguous diff segment.)
All the factory config of section B (0x030000-0x07AFFF, 0x07F000) is gone,
overwritten with vendor bitstream bytes.

=============================================================================
D. GOLDEN BANK (golden-bank.bin, flash 0x200000-0x2AFFFF)
=============================================================================
A complete, self-consistent Lattice bitstream:
  header "Date: Sat Jul 09 14:10:43 2022", Diamond 3.10.3.144, Final 10.27
  all 7562 frame CRCs valid
  no holes: only 0xFF run is the tail 0x08ED24-0x0AFFF7 (bank-relative)
It matches NONE of the five archived vendor images (34-37% byte match, i.e.
chance level). It is a build we do not have.
Its 2304-byte EBR init block is byte-identical to 13.39 / 9.53 / 6.69 / 16.53
and DIFFERENT from 10.81 (which has the known five-entry-longer prologue).

vendor library. None of these were read.
  0x0A0000 HDR gamma / ROE multi-bright     0x0B0000 module mapping   (dumped)
  0x1C0000 basic-param overflow chunk two   0x1E0000 factory bright/current
  0x1F0000 driver-chip params               0x390000 route table Ex
  0x3A0000 / 0x3C0000 gamma calibration     0x3B0000 data remapping
  0xD60000 basic-param overflow chunk one   0xE70000 anti-pixel sequence
  0xE80000 shutter sync                     0xE90000 multi-module param
An addrHi of 0xE9 implies a >=16 MB (128 Mbit) address space.
