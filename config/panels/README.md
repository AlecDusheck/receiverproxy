# Panel specs

One TOML file per module class. `[meta] status` says what the values rest on:
`verified` (driven on a bench; the notes name the card and firmware),
`derived` (taken from vendor configuration files; the notes say how many
agreed) or `stub` (a placeholder not expected to work).
`p25-128x64-sm16269s.toml` is the only `verified` spec.

## The derived specs

Generated by `scripts/corpus-mine.py`: one spec per (module size, scan, chip)
seen in at least 6 vendor `.rcvbp` files (the popular module classes only) whose pixel maps fit the generator's
wiring formula exactly (block, reversed groups, reversed lines) in a majority
of those files. Each file's `[meta]` table gives the counts (`sources`, the
files that fit; `agreement`, their share of the class) and three of the
source files by name.

A derived spec is the vendor's answer for that module class, written in our
schema: module geometry, serial clock, data groups, line direction, current
gains and wiring, with a derived chip library from `config/chips/`. None of
them has driven a panel.

Not emitted: geometries whose wiring the formula never fits, mostly the
1/2, 1/4, 1/5 and 1/10-scan outdoor modules (80x40 1/10, 40x20 1/5, 32x16 1/2),
whose chains snake through the line groups. Adding that pattern to
`crates/rcvbp/src/spec/mapping.rs` and the script's `generated_map` would
cover them; its log lists each skipped group with how many files fit.

Use one as a starting point for a new module of that class: copy it next to
the working spec, set `[screen]` to the cabinet size, and follow
`docs/provisioning.md`.

Regenerate with `python3 scripts/corpus-mine.py`; do not hand-edit.
